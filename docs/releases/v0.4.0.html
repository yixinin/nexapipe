What's new

0.4.0 follows 0.3.0, released 29 September 2026. Nothing in it breaks a working configuration: with no [timeouts] section the server dials exactly as 0.3.0 did, and the desktop app reads its credential store with the key it already had.

Desktop: the app asks the operating system first

  • Showing a TOTP secret, a node's connection string or this endpoint's Node ID now goes through the machine's own confirmation: Touch ID or the account password on macOS, Windows Hello or the account password on Windows, PAM on Linux. The store was already sealed at rest; what was missing was anything asking before handing a value back. This is the desktop half of the door the Android app got in 0.3.0.
  • One confirmation covers the next two minutes, so reading three credentials is not three prompts in a row.
  • A machine with nothing to confirm anybody with — no password, no fingerprint, nothing enrolled — is refused rather than quietly downgraded, and the app says why instead of failing silently. There is deliberately no app password of its own: a credential to forget, reset and attack.
  • Starting, stopping and restarting the proxy is deliberately not gated: it has to come back by itself after a reboot, with nobody there to confirm anything.
Not yet watched running on every platform. The gate compiles on macOS, Windows and Linux, the two-minute window it opens is pinned by unit tests, and the macOS prompt has been driven by hand. What has not been seen is the prompt itself on a Windows or a Linux machine — if one misbehaves, that is the part to look at first.

Backends: refusing what is already known

  • A route whose backends are all unhealthy now depends on how many there are. One backend is still handed out, because with nothing to choose between the health information buys nothing. Several, all down, refuse without dialling: the answer is already known, so a connect timeout was only ever spent delivering this refusal late.
  • A refusal says which it is. No route serves the host: 404, as before. The route exists and nothing behind it is healthy: 503. An L4 flow says the same on the wire with Status::BackendFailed.
  • least_conn joins round_robin and random: the healthy backend with the fewest requests outstanding gets the next one.
  • [timeouts] — connect_secs (default 10) and response_secs (default 30), each covering one step of talking to a backend. Read once at startup; 0 and anything past 3600 are refused at load.
# config.toml
[[routes]]
host_pattern = "app.example.com"
strategy = "least_conn"
backends = ["http://10.0.0.1:8080", "http://10.0.0.2:8080"]

[timeouts]
connect_secs = 10
response_secs = 30

The client's DNS cache answers only what it holds

  • Entries are keyed on QCLASS as well as on name and type, so one class is no longer served from another's answer.
  • They are keyed on the resolvers that produced them, so changing the configured DNS servers no longer keeps serving what the previous ones said.
  • A hit rewrites each record's TTL to the part that is actually left, so an answer fetched minutes ago does not go back out with its full TTL again.
  • A zero TTL is not cached. It used to get a one-second floor, and by RFC 1035 it means do not cache at all.

Linux: the keychain really holds the key

  • The desktop app's claim that the OS keychain holds the credential store's master key was not true on Linux, where the key was a 0600 file beside the ciphertext. Linux now uses the Secret Service, and an install that already had a file key keeps it — the same key moves into the keychain, because a fresh one would leave every credential in the store undecryptable.

Android: it asks before taking another app's VPN

  • Android allows one VPN slot per user, and establish() revokes whoever holds it without asking anybody. Nexa used to look only at the default network, so a per-app or split-tunnel VPN was invisible and was dropped silently.
  • Every VPN Android reports is now detected, and the first connection asks: take over, or cancel. Cancel costs nothing — nothing has been started yet.
  • "Remember my choice" is optional and can be taken back from the settings, because a remembered cancel must not become a setting you cannot find again.
  • An always-on VPN is refused outright, and says why: Android restores it immediately, and it may be a work-profile VPN you are not allowed to break.
  • Taking the slot is never automatic: a rebuild after a network switch no longer revokes another app's VPN by the way.

Changelog

Added

  • Desktop: a door in front of the credentials the app holds, described above — the operating system confirms the user, and stays open for two minutes afterwards.
  • least_conn as a third load-balancing strategy, alongside round_robin and random.
  • [timeouts]: connect_secs and response_secs, covering one step each of talking to a backend.

Changed

  • A route whose backends are all unhealthy now depends on how many there are: one is still handed out, several refuse without dialling.
  • A refused HTTP request distinguishes why: 404 when no route serves the host, 503 when the route exists and nothing behind it is healthy. An L4 flow says the same on the wire with Status::BackendFailed.

Fixed

  • The DNS cache in the TUN proxy answered more than it knew: entries were keyed without QCLASS and without the resolvers that produced them, a hit rewrote only the transaction ID, and a zero TTL got a one-second floor instead of not being cached. Those tests now run in CI, which had only been compiling them.
  • Linux: the desktop app's credential store keeps its master key in the Secret Service rather than in a file beside the ciphertext, as both READMEs already claimed.
  • Desktop: a node's connection string no longer sits in localStorage in the clear. A ticket is a credential — it names an endpoint and carries how to reach it — and it now lives in the encrypted store with the rest.
  • Desktop: masks are computed in Rust rather than in the UI, so a full value no longer reaches the page that is drawing it shortened, and an invite's secret is filed by Rust instead of being handed to the frontend in full.
  • Android: another app's VPN is no longer disconnected without asking. The guard detects every VPN Android reports rather than only the default network's, and the first connection asks instead of refusing — or silently revoking.

Before upgrading

Downgrading the desktop app means re-importing the invite. A node's connection string moved from the config payload into the encrypted store. A newer build migrates it on the way in; an older one reading the new payload finds nothing and drops the node. Upgrading keeps the node — going back does not.
  • Nothing changes by default: with no [timeouts] section the server dials exactly as 0.3.0 did.
  • A route with several backends that are all down now answers 503 without dialling, where it used to spend a connect timeout per request. A single-backend route is unchanged.
  • Desktop: the first credential you reveal asks the machine to confirm you. On Linux, where there is no system prompt to borrow, the app asks for your login password itself.
  • Desktop: bundles are signed, so an in-app update from 0.3.x verifies as usual through latest.json.
  • Android: the first connection asks if another app's VPN holds the slot. Cancel leaves that VPN running and Nexa stopped; a remembered choice can be changed in the settings.
